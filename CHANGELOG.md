# Changelog

All notable changes are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html); versions before 1.0 may change the
API between minor releases.

## [Unreleased]

### Added

- Adds `--ifc-timestamp <timestamp>` (an ISO-8601 timestamp or Unix epoch seconds; `IfcExporter.Timestamp` in the library) to write a fixed UTC timestamp into the STEP `FILE_NAME` header so repeated IFC exports of the same input are byte-for-byte identical, and adds CI-runnable corruption and fuzz tests over synthetic `.rvt` containers and inner streams with execution-time and memory-allocation bounds alongside full Windows, Linux and macOS CI test matrices. (Closes #39)

### Changed

- Reading: a profile roof's own area is no longer computed from the faces of its geometry (`ProfileRoof` step history and G-element graph, read for the current IFC profile only). Since the current profile writes the stored host area as `ProjectedArea`, as Revit's exports do, nothing read it. Measured on six project files of Revit 2020, 2022 and 2024: the IFC of both profiles is identical.
- Reading: in a file without its own class schema (Revit 2022) whose partition streams are read by their framing, the block reader, which collects the classes, geometry and other per-element facts of every element, reads the records of the project's own block as the framing lists them, in their current copy, instead of scanning the stream for anything that looks like a block. A record that runs into the next segment of its stream is read too; the blocks of the documents of loaded families, whose element ids repeat project ids, are no longer read as project elements. The geometry of a record that runs into the next segment or holds more than 1,000,000 bytes is not decoded, as the scan never reached it (the decoder takes up to minutes on such a record). Measured on 26 project files against the branch this starts from: the IFC and the compact JSON of 25 are identical; the export report of 22 differs in the elements it counts (ids that only a family document held are no longer counted) and in the category of ids that the Revit API does not return. In one architectural file 8 sketch lines change their length and 14 walls the name of their type: these elements keep two copies from different increments, which the increment table does not tell apart, and the reader now takes the other copy. Against Revit 2022, 5 of the 8 lengths are now right and 3 were right before (6465 of the 6482 sketch lines of the file are right, 6463 before), and the type name of the 14 walls is wrong both before and now. In the element list of `RvtDocument` of one test file (59,201 entries before), the 8,135 elements Revit returns keep their category, type, name, parameters and references; of the entries Revit does not return as elements, 49 without a category are gone and 50,738 change (fewer parameters on 50,564 of them, 3,737,513 parameters in all before and 3,161,540 now, and a name on 16,373). Not changed: which of two such copies is current. Refs #48.
- Reading: a file with its own class schema (Revit 2020, 2021 and 2023 to 2027) whose partition streams are all read by their framing, read in the Revit 2022 layout (`RvtReaderOptions.R22Layout`, which the IFC export, the solid quantities of the compact JSON and `RvtSceneReader` use), has the records of the project's own block rewritten into that layout as the framing lists them, and the block reader reads those records instead of scanning the rewritten stream, as it does for a Revit 2022 file. Read without the Revit 2022 layout such a file is read as before. Measured on 30 such project files against the branch this starts from: the IFC of all 30 is identical, and so is the number of exported elements; the compact JSON of 29 is identical, and in one architectural file 48 detail components now write an empty Area and Volume, as the reference does for all 84 detail components of the file (36 before). The export report of 15 files differs: 2,848 ids that only a scan of the stream found are no longer counted, and the category of elements that Revit returns without one changes. On the three files Revit 2022 opens, Revit returns none of the 1,025 ids that are gone and all the elements it returns are still read; of the 13,493 elements whose category changes, 960 now have Revit's category, none lost it, and 12,533 have a category where Revit has none, before and now (before, most of them were walls: 14,364 walls in a file where Revit returns 540, now 878). Refs #48.
- Reading: in the Revit 2022 view of a file with its own class schema whose partition streams are all read by their framing, the class root of every element is counted from the records of the project's own block, as for a Revit 2022 file, instead of by the stream walk, which counted the root of an element the element index had seeded once more, so that no such element counted its root once. The seed stays for a root the count leaves out, such as one whose rewrite into the Revit 2022 layout failed. Measured on the 30 files of the entry above against it: the compact JSON and the export report of all 30 are identical, and the IFC of 20 differs. Walls change their placement and body: in the Revit 2021, 2023 and 2024 saves of one architectural project 137 of 138, 167 of 169 and 154 of 169 changed walls are now written as in the Revit 2022 save of the project, and no wall that was written so before changes; in the Revit 2020 and 2025 saves of the test project all 48 walls are, 30 before. Against the reference IFC of 19 of the files, only the `BaseQuantities` `Length` of stair runs changes, which the runs now get as the Revit 2022 reader gives it: 30 runs in 9 files now have the reference's value, and 9 have one where the reference writes none (three runs of the same stairs in three saves, which the Revit 2022 save of the project writes so already). Refs #47.

### Fixed

- Reading: resolved project phase order and zero-id `ProjectPhase` elements in framed and 32-bit files by reading `AllProjectPhases` (class `187`) from the project's framed root records instead of scanning embedded family blocks, routing duplicate `AllProjectPhases` copies across multi-partition files via `DocumentIncrementTable`, and allowing `ProjectPhase` id `0` in `ElemTableReader`, `TfStreamWalker`, `TfBlockDeserializer`, `StairComponentSource`, `ElementBuilder`, and `ParseFramedBlocks`. (#56)
- IFC export, current profile: three rules copied from the ODA SDK 27.7 example exporter now follow Revit's exports, as the legacy profile already did. Columns with a `Pset_QuantityTakeOff.Reference` get `Pset_ReinforcementBarPitchOfColumn`. A roof's area in `Pset_RoofCommon` is `ProjectedArea`, the stored `HOST_AREA_COMPUTED`, where the current profile wrote it as `TotalArea` (with the area recomputed from the roof's own profile for an extrusion roof), and roof containers get it too. Stairs and stair flights get `NumberOfRiser` and `NumberOfTreads`. On a Revit 2022 model with Revit's IFC2X3 export, the column pitch set (3 of 3) and the stair and flight counts (12 of 12 values) now equal Revit's, none before; on `rac_advanced_sample_project` 2020 against Revit 2021's public IFC2X3 export the column pitch set equals Revit's on 176 of 176 columns and `ProjectedArea` on 4 of 5 roofs (none before). Revit's `TotalArea`, the live sloped area, is still not written. The legacy profile is unchanged.
- IFC export: `Pset_RailingCommon.Height` of a railing is its type's top rail height in the current profile as in the legacy one (in the project's length unit), where the current profile wrote 0 (an `IfcPositiveLengthMeasure` must be positive, and no Revit export writes 0). On a Revit 2022 model with Revit's IFC2X3 export it now equals Revit's 1100 on 10 of 10 railings. Files read by their own class schema (Revit 2020, 2021 and 2023 and later) now read the type's `m_topRailHeight` too, which only the Revit 2022 layout did (measured on samples of Revit 2020, 2024 and 2025; 2021 and 2023 files were not run): `rac_advanced_sample_project` 2020 equals Revit 2021's public IFC2X3 export on its 9 comparable railings (1219.2; none before).
- IFC export: a parameter named for a property with its set, such as `Pset_BeamCommon.LoadBearing`, now gives the value ahead of one named for the property alone, as in Revit's exporter (revit-ifc reads `Pset_X.Prop`, then `Prop`, then on a type the same names with `[Type]`). This covers `LoadBearing` of beams, braces, columns and column and beam types, `IsExternal` of types, railings and stairs, a mullion type's `Span`, a ceiling's `Finish`, the stair counts and dimensions a named parameter blocks, and the named `PitchAngle` that keeps the legacy profile from writing 0. The `IsExternal` of the other occurrences reads the set of its own class too (`Pset_MemberCommon`, `Pset_PlateCommon`, `Pset_ColumnCommon`, `Pset_SlabCommon`, `Pset_BeamCommon`, `Pset_RampCommon`, `Pset_DoorCommon`, `Pset_WindowCommon`), in both profiles; the classification a hosted element or a window inherits from its host still reads the property name alone. On walls and curtain walls a set-qualified `IsExternal` keeps the type function from giving the value of their own property, as the property name does. Nothing moves on files without such parameters.
- IFC export, current profile: a curtain wall mullion's `Pset_MemberCommon.Span` is written from the same exact sources as in the legacy profile (the instance's Span or length parameter, else the length of its validated body), where the current profile wrote none. On Autodesk's `rac_advanced_sample_project` (the Revit 2020 sample against Revit 2021's public IFC2X3 export of it) it equals Revit's value on 3,205 of the 3,276 mullions and differs on none; the other 71 have no exact source and stay without it. On a Revit 2022 model with Revit's IFC2X3 export it equals Revit's on all 144. In both profiles a mullion parameter named `Pset_MemberCommon.Span` now gives the value ahead of one named `Span` and of the length, as it does in Revit's exporter.
- Reading: a wall's top attachment (`JoinToRoofGStep` with `m_baseOrTop` 1, which gives `Pset_WallCommon.ExtendToStructure` and the Top is Attached parameter) is read whatever the `m_version` of the wall's geometry steps, where it was read only for the step versions of the files the layouts were taken from. `ExtendToStructure` now equals Revit's value on all 146 walls of Autodesk's `rac_advanced_sample_project` (the Revit 2020 sample against Revit 2021's public IFC2X3 export of it; 40 before), and a wall reads the same in every save of its project on the samples of Revit 2020 to 2025. The rule follows rvt-rs RE-228 and RE-284. A wall parameter named `Pset_WallCommon.ExtendToStructure` now gives the value ahead of one named `ExtendToStructure`, as it does in Revit's exporter.
- IFC export, current profile: `Pset_WallCommon.LoadBearing` takes the value of a wall parameter named `Pset_WallCommon.LoadBearing` or `LoadBearing` where there is one; otherwise it is true only when the wall's Structural box (`WALL_STRUCTURAL_SIGNIFICANT`) is set and its Structural Usage is Bearing, false otherwise, and left out when either value is not read exactly. It was true on every wall. It now equals Revit's value on all 146 walls of Autodesk's `rac_advanced_sample_project` (the Revit 2020 sample against Revit 2021's public IFC2X3 export of it; none before) and on 55 of 55 walls of two Revit 2022 models with Revit's IFC2X3 exports (18 before). The rule follows rvt-rs RE-429.
- Geometry meshing: scales the pole Jacobian degeneracy threshold in `RevolvedMesher.NormalAt` by the profile tangent magnitude so 1-ULP trigonometric differences at sphere poles fall through to the pole limit normal on Linux and macOS as on Windows instead of leaving duplicate pole vertices unmerged. (Refs #39)

## [0.4.0] - 2026-11-13

### Breaking changes

- Legacy IFC profile: the `GlobalId` of a type-level `IfcRelAssociatesMaterial` relation is now seeded from the material element id list (`type-materials:{materialIds}`, as `materials:{materialIds}` already is for product-level relations, and `type-layer-set:{seed}` from the host type id or layer-set group key) instead of the STEP entity number of the relating material, material list or layer set. Type-level material relation `GlobalId`s in the legacy profile change once and no longer shift when entities are added or removed earlier in the file; product-level material relations and the current IFC profile are unchanged. (Closes #88)

### Added

- Preview project `src/RvtIO.Scene`: `RvtSceneReader` turns a document into a scene of the `IOScene` 0.1 contract, with the element meshes in metres (shared symbols as instanced geometry), the Revit UniqueId as the source id, the IFC GlobalId of Revit's IFC export as the IfcGuid, names, categories, materials and the instance and type parameters as property sets of their display text. See [the scene adapter](docs/scene.md).
- Package `RvtIO.Scene`: the scene adapter is now published on the RvtIO release tag, depends on exactly the same RvtIO version and references IOScene with the range `[0.1.0, 0.2.0-0.0)` (a release that would depend on an IOScene preview, or on a version nuget.org refuses in a dependency, fails).
- API: `ElementMeshes.Extract` (namespace `RvtIO.Meshes`) returns the triangle meshes of the drawable model elements of an opened `RvtDocument`, in feet, without reading the file again: per element its own triangles (one mesh per material, flat normals, counter-clockwise around them) and, for an element that is exactly its family symbols placed rigidly, the placements of shared symbol meshes in the frame of the family, with a coverage per element (complete, partial, box in place of a rescaled symbol, no geometry, undecoded; partial also when a placed symbol or a symbol nested in one has no geometry, or a Geometry node that Revit exports has no decoded polygon). A cut or clipped instance, an instance with faces of its own and a scaled one keep their own triangles; a mirrored placement keeps the winding of its symbol and carries the mirror in its transform. The drawable elements follow a subset of the product rules of the IFC export of the current profile (listed in the `ElementMeshes` remarks, with those not applied, such as the "export to IFC" flag and topography, so the meshes can include elements the IFC leaves out); the face materials and the hidden Geometry nodes follow its rules. The types are listed in [the public API](docs/public-api.md). IFC and JSON output is unchanged.
- CLI and diagnostics: `--strict` exits with code 6 (`RvtExitCodes.PartialRead`) instead of 0 when a read finishes partial without exceeding a reader limit (a stream member failed to decode, was rebuilt by structural recovery, or decoded without a matching checksum, or `Global/ElemTable` decoded no row). Nothing is exported when exit code 6 is returned; `limits.strict` records the option and `issues[]` lists the affected streams and reasons (`failed-members`, `recovered-members`, `unverified-members`, `no-rows`) alongside `streams[]`. Default behavior without `--strict` is unchanged. (Closes #54)
- Default output, current IFC profile: every beam with a straight drive curve gets `Pset_BeamCommon.Slope`, the angle in degrees of its drive curve to the horizontal (0 for a horizontal beam, never negative), whether or not BaseQuantities are exported and whatever its body; its quantities are unchanged. A beam without a straight drive curve gets no Slope.
- Default output, current IFC profile: `Pset_BeamCommon.Span` of a beam without a stored length is the length of its straight drive curve; a beam without one has no Span.
- Default output, current IFC profile: a round column gets the volume and surface of the measured node that carries its two exact end faces in place of the open tessellated side. A round column is a vertical cylinder: exactly two exact planar end faces, horizontal, without holes, of at least eight corners on one circle (the same for both faces), each with an exact area within 0.5% of the area of that circle (a regular polygon of 32 corners or fewer is refused), and every other face with its corners on the cylinder between the end faces. The node is taken only when it is the one node that holds nothing but end faces. It is used for `NetVolume` after the sources that come first for a column (the Medium solids, the nominal area of a tube, the computed host volume, the measures of all nodes) and for `CrossSectionArea` (half the surface) of a column without extrusion data. When the two end faces also have the same exact area (a vertical prism) the column gets the extrusion data `Length`, `CrossSectionArea` (the area of its circle), `OuterSurfaceArea` and `GrossVolume`. Other columns are unchanged. Measured on the round columns of one sample (corner distances to a millionth of the radius, or eight units in the last place of a 32-bit coordinate where that is more).
- Default output, current IFC profile: `Pset_ColumnCommon.Slope` (90 degrees for a vertical extrusion) is written for every column with a body of its own, whatever its shape, not only for the first column of its type; the columns that share a mapped body still carry it on the first one, and a column whose body is not recognised keeps the previous rule (the first column of its type). A round column (as above, with end faces of the same exact area) is judged on all its faces, its exact end faces being listed outside the tessellated shell of its side; other columns are judged as before. Compared with the reference only on the round columns of one sample (Slope equal on all 152); the columns of two other samples, which are not round, are unchanged.
- IFC export: a structural framing element whose structural type is Brace is an `IfcMember` (and its type an `IfcMemberType`) in every file, not only in files whose geometry is not decoded; before, a brace of a Revit 2022 file was an `IfcBeam`. Its `Pset_MemberCommon` carries `LoadBearing` (the occurrence parameter, else true), as does that of its type in the current profile, and, in the current profile, a `Span` that is the exact length of the straight drive curve (the stored length, which the file rounds to under 0.1 mm, only when there is no such curve); a mullion gets neither. A brace with a straight drive curve gets `Pset_MemberCommon.Slope`, the angle of that curve to the horizontal, as a beam does, in every file and not only where the body is decoded (current profile). In a file whose geometry is decoded the `Length` and `CrossSectionArea` of a brace stay those of the beam rule, the profile length and area; its other quantities are `NetVolume` and `NetSurfaceArea`. A brace loses `Pset_BeamCommon`, as it is no longer a beam. In a file whose geometry is not decoded (Revit 2023 and later) the `Length` and `CrossSectionArea` of a brace keep the member rule, where the section is half the surface area of the solid. The legacy profile also writes a brace as an `IfcMember`, with `LoadBearing` but without `Span` and without the type-level set. In a Revit 2023 file, where braces already were members, the type-level `Pset_MemberCommon` is now written for them too (current profile). Measured against the reference on one Revit 2022 sample (all 22 braces: class, type, `IsExternal`, `LoadBearing`, `Reference` and `Span` equal), three synthetic Revit 2022 models and two Revit 2023 samples (`LoadBearing` and `Span` of all 81 braces equal); the `Length` and `CrossSectionArea` of the Revit 2022 braces are unchanged from the beam output. The reference writes no `Slope` for a brace, so this property is a deliberate difference from it. Beams are unchanged.
- IFC export, current profile: a structural framing element whose structural type is Non-structural is an `IfcBuildingElementProxy` (and its type an `IfcBuildingElementProxyType`) instead of an `IfcBeam`, with its quantities and `Pset_BuildingElementProxyCommon`. Measured on one Revit 2021 structural file only (18 of 18 such elements agree with the reference), not on a Revit 2023 or later file; the legacy profile is unchanged.

- IFC export, current profile: ducts, pipes, conduits and cable trays of files with their own class schema (Revit 2021 and 2023 and later) take their length from the straight drive curve of the element, as those of a Revit 2022 file do, so each one carries the Length property of `Pset_FlowSegmentDuctSegment` and `Pset_FlowSegmentPipeSegment` (the curve length in millimetres) and the parameters derived from the curve (surface area, elevations, slope) that the reader had left unset in those files. A driver that is an arc, or that holds no straight curve and is not the spline of a flexible duct or pipe, gives no length, as before.
- IFC export, current profile: flexible ducts and flexible pipes carry the Length property of `Pset_FlowSegmentDuctSegment` and `Pset_FlowSegmentPipeSegment`, the arc length in millimetres of the Hermite spline that drives them. A flexible pipe of a Revit 2022 file already had it; a flexible duct of a Revit 2022 file did not, and neither did a flexible duct or pipe of a file with its own class schema (Revit 2021 and 2023 and later), whose spline nodes were not read. Measured against the reference on five files: all 113 flexible ducts of a Revit 2022, a Revit 2023 and a Revit 2024 sample (113 of 113 in each, equal within 1e-6 relative) and the 6 flexible ducts and pipes of a Revit 2021 and of a Revit 2023 sample (6 of 6 in each) now match; nothing regressed or was lost in those samples. A spline whose nodes are incomplete, or a driver that queues more than one spline, gives no length, as before. Files of Revit 2020 and of Revit 2025 and later were not measured.
- IFC export, current profile: the ducts, pipes, conduits, cable trays and pipe insulation of a Revit 2021 file are named after the English name of their system family, as those of a later file are (`Pipe Types:{type}:{id}`, `Rectangular Duct:{type}:{id}`, `Cable Tray with Fittings:{type}:{id}`, `Pipe Insulation:{type}:{id}`) instead of after the `OST_` category name. The other system families of a Revit 2021 file are the subject of the entries below, and the MEP curve families of a Revit 2020 or earlier file keep their category names.
- IFC export, current profile: the curtain walls and stairs of a Revit 2020 or 2021 file are named after the English name of their system family, as those of a later file are (`Curtain Wall:{type}:{id}`, `Assembled Stair:{type}:{id}`, `Stair:{type}:{id}` for a stair of the older record layout) instead of after the `OST_` category name, so the parts that aggregate to them (mullions, plates, railings, slabs, doors, windows and stair flights) carry the same parent name; the names of some members and slabs change with it. The English name is used whatever language the file was saved in, as for the Revit 2021 MEP curves. A curtain wall of a Russian Revit 2020 file no longer takes the family name of a mullion. Measured on Revit 2020 and 2021 sample files (only Assembled Stair occurs in them; the names of Cast-In-Place Stair and Precast Stair follow the stored stair kind and are covered by unit tests only). The other system families of these releases are the subject of the entries below, the MEP curve families are named for Revit 2021 only, and the legacy profile is unchanged.
- IFC export, current profile: the floors, foundation slabs and building pads of a Revit 2020 or 2021 file are named after the English name of their system family, as those of a later file are (`Floor:{type}:{id}`, `Foundation Slab:{type}:{id}`, `Pad:{type}:{id}`) instead of after the `OST_` category name, so the `ObjectType` of the slab and the name of its material layer set (`Floor : {type}`) change with it. The English name is used whatever language the file was saved in, as for the curtain walls and stairs of those releases. A floor whose type is a foundation slab type is a `Foundation Slab`. Measured on ten Revit 2020 and 2021 sample files (three of Revit 2020, which also hold a foundation slab and two pads): 1638 slab Name and ObjectType slots now agree with the reference where none did (1190 in one structural file, then 236, 96, 42, 22, 22, 10, 10, 8 and 2), none regressed, and the 44 renamed material layer sets of seven of those files match the reference by name. Files of Revit 2022 and later are byte-identical to before, the compact JSON is unchanged, and the legacy profile, which requests no locale, is not changed by construction (not measured). Six slabs of one file keep a type name that differs from the reference; that defect was there before and is not changed.
- IFC export, current profile: the walls, roofs, ceilings, railings and stair parts of a Revit 2020 or 2021 file are named after the English name of their system family, as those of a later file are (`Basic Wall:{type}:{id}`, `Basic Roof:`, `Sloped Glazing:`, `Compound Ceiling:`, `Railing:`, and for stair runs and stringers or carriages in the `ObjectType` `Non-Monolithic Run:`, `Monolithic Run:`, `Stringer:`, `Carriage:`) instead of after the `OST_` category name. The names of wall openings, of the material layer sets of walls, roofs and ceilings and of the parent roof of curtain panels follow. The English name is used whatever language the file was saved in; the legacy profile, which requests no locale, is not changed. Measured against the reference on ten Revit 2020 and 2021 sample files (three of Revit 2020), compared with the build before this change: 4309 IFC slots now agree with the reference where none did (2335, 1055, 393, 216, 132, 130, 21, 21, 4 and 2 per file), and no slot regressed, was lost or was added. 2313 products were renamed (by GlobalId): 2282 of them have exactly the reference values in every slot that changed, 13 (12 wall openings and one curtain wall) have no reference element under the same GlobalId, and 18 keep a changed slot that still differs from the reference (see below); 142 material layer sets were renamed. Files of Revit 2022 and later (five samples, and a Revit 2021 file without these families) are identical to before apart from the file header timestamp, and the compact JSON is unchanged in the thirteen files where it was compared (seven of the ten files above, that Revit 2021 file and the five later samples; it was not compared for the other three of the ten). The legacy-profile export of four of the ten files (two of Revit 2020, two of Revit 2021) has an identical data section; the other six were not measured in that profile. Not given a family name: wall sweeps and stair landings, which both occur in the samples; a wall sweep already carries the same name as the reference and a stair landing is named after its type, as the reference names it, so neither needs one. Not changed either: the elements whose type the reader does not resolve and which therefore have no type name: 8 strip footings of two files keep the `OST_` name (their type link is present in the file and is not read yet; the `Wall Foundation` name is in the list but affected no element), and 5 stair flights of one file keep it (in the `Name` and the `ObjectType` of three of them, in the `ObjectType` of the other two; why their type is not resolved was not traced). - Default output, current IFC profile: a column whose base level is a Level that is not a project storey is contained in the highest storey at or below that level, and in the building when no storey is that low, instead of the storey chosen by the bottom of its body. Measured on structural columns of one project; the building container of a column below the lowest storey is not checked against Revit.
- Default output, current IFC profile: a duct, pipe, cable tray, conduit, fitting, accessory, insulation, terminal, sprinkler, or an electrical, lighting, mechanical, plumbing or food service equipment or fixture whose level is a Level that is not a project storey is contained in the highest storey at or below that level, and in the building when no storey is that low, instead of the storey chosen by the bottom of its body (the same rule as for columns on such a level). A nested element reads that level from its top-level instance, as it already did for a level that is a storey. For a family instance the base level is read before its own level parameters, so a base level that is not a storey decides the container as one that is a storey already did. Measured on three Revit 2021, 2023 and 2025 saves of one building-services project and on two saves of a second one, by the container of the products that both the output and the reference write: 653 of 6404 (2021) and 652 of 6404 (2023, 2025) products were in another container than in the reference, now 8 and 7; 3 of 4929 and 3 of 4898 in the second project, now 0. - IFC export: a roof that has no body of its own and holds curtain mullions or panels is written as an `IfcRoof` that aggregates them (`IfcRelAggregates`: mullions as `IfcMember`, panels as `IfcPlate`) in a file whose geometry is not decoded, as it already was in Revit 2022 files; its children are no longer contained in a storey. Measured against the previous build: Revit 2023 to 2026 files (arch23, school23, goldenarch23, dach24, racadvanced26) gain 12 or 120 aggregated mullions and 8 or 42 plates and the aggregate and container slots of the roof children now match the reference, with no regressed slot (measured with the current profile; the legacy profile was not measured); a Revit 2021 file gains the same aggregate under the right roof; the parent roof there is named as the reference names it by the entry on the walls, roofs, ceilings, railings and stair parts above (current profile). The Revit 2022, racbasic21 and jparch21 samples are unchanged.
- IFC export: a curtain panel or mullion that names its curtain wall only by the plain host id (no curtain host id) joins the `IfcRelAggregates` of that wall, under the same checks as before (curtain wall function, not a basic or stacked wall, no IFC override, single occurrence); a curtain host id, when present, still wins, and doors, windows and walls are still matched by the curtain host id only. In one Revit 2025 sample this adds 60 mullions and 13 panels to the aggregates of their curtain walls, with no regressed slot; the curtain-wall aggregates of one Revit 2021 sample also grow by one mullion and two panels, which was not traced to a rule.
- IFC export: the bars of area reinforcement (`RebarInSystem`) of Revit 2020 and 2021 files are written as `IfcReinforcingBar` with the group of their system, as those of later files already were. Shape data that is not valid (a direction, a length, a projection or a diameter that is not a finite number, a turn other than -1, 0 or 1, a diameter not smaller than the vector between the outer corners of the middle edge) gives no bar instead of an error. Before, the sides of the cut loop were named by the frame they are measured in, so a door 0.8 wide and 2.1 high got Height 0.8 and Width 2.1. Openings of curved walls and curtain walls, openings that nothing fills and openings of other fillers stay as they were. To get the earlier values, use the new `--ifc-opening-legacy-axes` command line option or set `IfcExporter.OpeningQuantitiesSwapped` to true. `--ifc-opening-host-axes` (the opt-in of the previous change) is still accepted and does nothing, and `IfcExporter.OpeningQuantitiesInHostAxes` still compiles; it is now true by default and the opposite of `OpeningQuantitiesSwapped`. Refs #6.
- Default output, current IFC profile: the IFC holds only the elements that exist in the last project phase. Elements demolished in the export phase or an earlier one, or created in a later one, are left out, with their property sets, quantity sets, types and relations. To get every element as before, use `--ifc-phase all` or set `IfcExporter.ExportAllPhases` to true; `--ifc-phase <id>` and `IfcExporter.ExportPhaseId` select one phase. Rooms follow the export phase unless a room phase is given. The legacy profile and the JSON output are not filtered by default.
- Default output, IFC quantities: base quantities of beams, columns, members, piles, floors and plates are derived from the surface integrals of the source geometry, and door and window height and width come from their parameters or frame extent before the bounding box. NetVolume, NetSurfaceArea, CrossSectionArea, Length, GrossArea, NetArea and the door and window Height, Width, Area, OverallHeight and OverallWidth can differ from 0.1.0; most values move toward the reference exporter. In the legacy profile members whose length is now derived can also gain the property Span. There is no option that restores the 0.1.0 values.
- Default output, stairs: a stair flight carries NumberOfRiser, NumberOfTreads, RiserHeight and TreadLength and the property set Pset_StairFlightCommon; runs, landings, stringers and railings of a stair are aggregated into the stair (IfcRelAggregates) and are no longer contained in the storey; a landing takes the name and Reference of its type. See also the stair type entry below. There is no option that restores the 0.1.0 layout.
- API: `RvtFileReader.Read` and `RvtDocument.Open` throw `RvtInputException` (or `RvtLimitException` for a stream over the platform array length) for a file that cannot be read, instead of an `EndOfStreamException`, `FileFormatException` or a similar exception from a decoder. Code that catches the old exception types must catch the new ones.
- Command line: the exit codes 2, 3 and 4 are new (see below). A damaged or truncated file ended in an unhandled exception in 0.1.0 (or, when only the end of a stream the export does not use was missing, in an export without a message) and now returns 2 with a one-line message.
- Default output, current IFC profile: the GlobalId of the IfcStairFlightType of a stair run or landing changes, because its seed now contains the run style, and the type gets the predefined type STRAIGHT instead of NOTDEFINED (2 types in the Revit 2025 architecture sample, 4 in the Revit 2024 DACH sample). The IfcRelDefinesByType of those types follows.

### Added

- Exit codes 2 (input cannot be read: missing, empty, not a compound file, cut or damaged), 3 (a stream exceeded a reader limit and the read was cut) and 4 (a decoder failed on a readable file), and the options `--report`, `--allow-partial` and `--raise-limits`. A complete export without them is unchanged. See [the export report](docs/export-report.md). `RvtFileReader.Read` and `RvtDocument.Open` check that every stream of the compound file can be read to its declared end; `RvtReaderOptions.Diagnostics` collects the streams read and the limits that cut one. The report counts partial reads, written reinforcing bars and the assembly written for a beam system, and refuses a report path that names the input or the export output, also through a link.
- The `--ifc-phase <last|all|id>` command line option and the `IfcExporter.ExportPhaseId` and `ExportAllPhases` properties (see the breaking change above).
- The opt-in `RvtReaderOptions.ResolveCurrentCopies` reader option and `--resolve-current-copies` command line option, which keep only the current copy of an element that several partition streams hold. It is off by default and the default output does not change.
- The full JSON, and the IFC property sets written by `--ifc-revit-parameters`, get the parameter CURTAIN_WALL_PANELS_WIDTH (a copy of GENERIC_WIDTH) on elements that hold only the generic width; the full JSON lists it in ParameterDefinitions. CURVE_ELEM_LENGTH values can differ in the last digit. Compact JSON is unchanged.
- The IFC length unit is read from the project length unit in every file layout (including the Revit 2020 display unit layout and family documents), so a file whose length unit is not the millimetre now gets that unit in the IFC (a family in feet gets FOOT, SQUARE FOOT and CUBIC FOOT instead of millimetre, square metre and cubic metre); the reason is reported through diagnostics when it falls back to millimetres.
- Stair runs and landings resolve their type through the stored type association, so the IFC names the real type, writes its stair flight type and property sets, and the stair run Reference. The IFC stair shape of the current profile stays undefined when a stair has a sketched run, and a railing aggregated into a stair no longer takes the classification code of the stair. The run Length quantity keeps the inputs it had. The element class counts of the stair source are taken from the stream walk, which in files with their own class schema lets both profiles recognise the runs and landings of a stair.

### Fixed

- Reads the element table of a file whose partition stream carries padding after the last page segment of a paged gzip member (the Revit 2021 MEP sample project, Closes #8). Before, the table fell back to a decoder that returned extra bytes and the export held about half of the elements (13706 of 27583), most without properties or geometry, and elements that are not in the file. Output of other files is unchanged.
- Paged gzip members are decoded with an exact deflate end, and a missing trailer, a reserved flag or a wrong header CRC is rejected. A damaged or truncated partition stream is rejected by the framing check instead of read past its end.
- Selects the element table and record layout by the release of the file's own schema, the older of it and the saved release, and reports the release in the diagnostics. Decodes the document increment table of a file saved in several increments with a bound on the work it may do; a malformed table is rejected instead of guessed.
- `--ifc-room-phase` and the room phase property accept the phase id 0.
- Takes the length of a curtain wall mullion from the axis of its own symbol, and the footprint of a curved wall from the area of its rebuilt curve loop.
- IFC slab and plate quantities: the NetVolume of floors and of plates (IfcPlate) is taken from the source geometry too; values move toward the reference exporter (floors by 0.01 to 0.2 percent, the curtain louvres of the 2024 DACH sample by 7 percent). Floors that have no vertical prism gain a Width quantity.
- The Width quantity of foundation slabs (pile caps and base slabs), which since the base quantities change took the vertical side of the body instead of the first side of its profile (Closes #78). Other slabs take the world X extent of their vertical prism and fall back to the body only when they have none; this equals 0.1.0 for floors and pile caps, while base slabs and some roofs now equal the reference exporter.
- The NetVolume of round foundation piles whose solids are open shells without measures is written again (Closes #79). It is taken per node, only when the node is a straight prism (two opposite end caps, and at least one side face, all of them flat and parallel to the cap normal or cylinder faces along it, with their points on the cap boundaries), as the larger cap area times the distance of the caps, and added to the measured and closed solids of the foundation; a node below zero and a cutting node take no part, also not for the NetArea. 0.1.0 summed the open shells, which gave values up to ten times too large. A pile whose end caps differ by more than 2 percent still gets no NetVolume (#42).
- The extrusion of an opening that the door or window code rewrites from the final outline can change shape (profile size, extrusion depth, placement direction), independent of `--ifc-opening-legacy-axes`. Seen on one opening of the 2022 rac basic sample; the profile size and extrusion depth now equal those of the reference exporter.
- A door or window with a non-finite dimension is ignored for the opening, and each side of an opening is taken from the door or window independently.
- Legacy IFC profile: the GlobalIds of the type-level IfcRelAssociatesMaterial relations (and of the relations of layer sets) change in files where the output gains or loses entities before them, for example the mullion Span property in the Revit 2022 rac basic sample, because the legacy seed is the STEP number of the relating material. Ids of the current profile do not depend on entity numbers and are unchanged.

### Performance

- Reduces the memory allocated and the processor time spent in the tessellation of trimmed surfaces and in the ordering of boundary rings: grid cells are clipped in reused per-thread buffers and the ring search uses flat arrays instead of per-cell lists and LINQ. The output is unchanged byte for byte.
- Speeds up the export of models with many family instances: the record chunks are scanned for shared parameter GUIDs without an allocation per offset, face corner keys are sorted ordinally, and the faceted shells of the family symbols are planned on several threads before the writer needs them. The output is unchanged byte for byte. The processor time can rise because plans that the writer does not use are computed too, and single-core machines gain nothing.
- Together, the two changes above cut the wall time against 0.1.0 by 17 to 18 percent in single repeated runs of large JSON exports and by 2 to 3 percent in large IFC exports. Peak memory depends on the collector and can be higher than in 0.1.0.
